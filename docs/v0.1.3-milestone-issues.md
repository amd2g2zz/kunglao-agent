## A — feat: seed hypotheses before claim registration — make loop hypothesis-driven

**Why filed**: `#528` (closed) covers hypothesis *storage* and *restart rehydrate*. This issue is the *loop-flow half* — the agent never actively seeds hypotheses before chasing evidence. AES example: agent sees AES → dispatches "check hardcoded key" without first recording "I think this might be Cobalt Strike beacon" or "might be custom crypto". Without an upfront hypothesis, the agent cannot detect "evidence that contradicts my starting assumption".

**Proposed change**

After `task_spec.yaml` intake, before claim-register seeds, orchestrator drafts `H-NN` hypotheses for each `primary_question` (≥ 1 per question). Each `H-NN` carries the existing `competitor_group` + `candidates` schema. Creation logged via `kunglao_log`. Loop gains a record of "I initially thought X" before evidence gathering.

**Acceptance**

- Every `primary_question` has ≥ 1 `H-NN` before any `C-NN` dispatch.
- Hypotheses surface in cold-start digest (already wired via `digest_build.sec_g`).
- New failure mode: a hypothesis contradicted by PROVEN fact → flag in `convergence_check`.

**Out of scope**

- Hypothesis persistence / restart rehydrate (#528 closed, covers it).
- Hypothesis-driven dispatch (separate followup if needed).

**Related**: #528 (storage, complement not conflict), #626 (Decision Context compiler, adjacent).

## B — feat: anomaly detection layer — flag when evidence contradicts baseline

**Why filed**: `scripts/fact_contradiction_gate.py` detects **contradiction** between PROVEN facts (same topic, different conclusions, no `supersedes` link). It does NOT detect **anomaly** (a fact unusual against a baseline or expected pattern). A human analyst sees "TLS to 192.0.2.1:8443 from a binary with no other network code" and immediately thinks "anomaly, why?" — the current loop has no way to register that observation.

**Proposed change**

1. New `scripts/anomaly_detector.py`: given a new fact and a baseline corpus, compute an anomaly score in `[0, 1]`.
2. Baseline = known-good pattern set (RE-library refs + prior samples — `#358` re-library gap-fill will seed this).
3. Score above threshold (default 0.7) → auto-promote to `notes/` with new `boundary_type: anomaly`.
4. Surfaced in `convergence_check.py` DRAIN stage alongside `global_contradiction`.
5. Optional: feed high-anomaly facts into `hypothesis_store.py` as candidate competitors.

**Acceptance**

- Each new fact gets an anomaly score.
- Facts above threshold auto-promote to a note with `boundary_type: anomaly`.
- Anomaly count surfaces in `scripts/progress_report.py` output.

**Out of scope**

- ML-based anomaly detection — start with rule-based heuristics + RE-library baselines.
- Cross-sample baselines (separate issue if needed; deferred due to #358 / #626 scope).

**Related**: #358 (P4 v0.2 batch — re-library gap-fill may overlap; coordinate before merge).

## C — feat: intent-aware strategic stopping — stop when user question answered, not just open=0

**Why filed**: `#55` completion gate stops when task-oracle items are resolved (`open=0`). `#473` wired the closeout gate chain. Neither checks **"has the user's actual question been answered?"**. Oracle items are administrative scaffolding; the user's question is what they actually care about. A session can complete with `oracle=clean` while leaving the user's real question half-answered.

**Proposed change**

Layer an "intent check" on top of the existing completion gate:

1. On Stop event, after oracle check passes, compare `evidence/verdict.json` `primary_questions[]` against `task_text` (extracted from oracle at Phase 0).
2. If `primary_questions` doesn't cover `task_text`'s key questions → refuse Stop with "intent unmatched" reason.
3. New exit code 4 on `scripts/completion_gate.py`: `INTENT_UNMATCHED` (precedence after the existing 3).

**Acceptance**

- Stop hook refuses when `task_text` has unmet intents (even if oracle clean).
- Test fixture: oracle has 3 items, all closed, but `task_text` mentions a 4th unaddressed concern → completion_gate returns `INTENT_UNMATCHED`.

**Related**: #54 (premature termination — post-hoc detection, opposite direction), #55 (completion gate — extends, doesn't replace), #473 (closeout gate chain — adds layer, doesn't conflict).

## E — scope: re-evaluate v11 attribution removal (followup to #106)

**Why filed**: `#106` closed: verdict-scorer v11 removed actor/intent attribution ("kunglao-agent verifies RE analysis correctness/completeness against `task_spec.primary_questions`, **NOT threat scoring**"). Decision made 2026-08-12. Made scope boundary clean: kunglao-agent = RE verification; threat intel / actor attribution = separate tooling.

**New observations since v11**

- Multiple sessions where user asks "what is this sample" and the loop produces verified facts but no narrative answer.
- AES example: facts prove "uses AES-256-CBC" + "calls BCryptGenerateSymmetricKey" + "no hardcoded key" — but user still wants to know "what is this binary doing and who might have written it".
- The 4-dim verdict scope answers "are facts correct" but not "what does the user actually want to know".
- v0.1.3 milestone review surfaced this gap as "意图归因器" in the 5-business-gap list.

**Question for review**

Does the v11 boundary still serve users, or does it leave a gap that makes the loop "feel" less like a human RE analyst?

**NOT asking to add attribution back blindly**

This issue asks for **scope boundary re-evaluation**, NOT implementation. If the decision is to keep the boundary, this issue closes as `wontfix` with rationale documented in the handbook.

**Possible outcomes** (decided in this issue, not in implementation)

- **A**: Keep v11 (close as `wontfix`, document rationale).
- **B**: Soft add — narrative layer separate from verdict; "what is this sample" addressed without breaking scope.
- **C**: Reverse — add attribution back to verdict-scorer (would re-open #106).
