# 开发流程规范 — 串行交接链

> **核心判据：一道流程的正当性 = 它抓到过的真实缺陷 ÷ 它消耗的成本。**
> 答不出"它上次抓到什么"的流程，删掉，不管它看起来多标准。
> 这与 [unit_test_spec.md](unit_test_spec.md) 的四问是同一把尺子——那把量测试，这把量流程。
>
> 质量是前提，不是目标函数。在质量底线之上，求推进速度与 token 节约。
> 流程不是越多越好；最终对账的是交付质量。

## 0. 加一道流程前，先回答四问

| 问题 | 不合格的回答 |
|---|---|
| **它上次抓到的真实缺陷是什么？** | "更严谨" / "业界标准" / "应该有" |
| **没有它，那个缺陷会漏到哪一层？** | 答不出具体位置 |
| **它和哪个必然发生的动作重合？** | 完全独立 → 成本要单独算，不能白拿 |
| **删掉它，交付质量掉多少？** | 说不出 → 删 |

任意一问答不上来，不加这道流程。已存在的流程同样按这四问定期复审。

## 1. 形态：串行交接链

任务预先拆成有序的段，一段一个 subagent，串行接力。

**主 agent 只做两件事：启动链首、处理异常**（超时 / agent 死亡 / 申诉不收敛）。
不指挥、不中转、不读代码。下一段的输入是 **spec + 交接文档 + 代码**，不是主 agent 的指令；
拉起下一段时只给坐标（工作树路径、spec 路径、交接物路径），不给任务说明。

为什么串行而不是并行加专职评审者——**成本理由，不是严谨理由**：

- 下一段本来就**必须**读上一段的代码才能在其上继续工作。审查合并进这次必然发生的读取，
  边际成本接近零。
- 并行 + 专职评审者是两次独立冷启动读取，评审者读完即弃，那份读取成本完全不复用。
- 主 agent 退出读代码与中转，省的是整条链里最大的一块上下文开销。

## 2. 一个 agent 的四阶段生命周期

阶段属于**一个 agent 的生命周期**，不是流水线的工位。每个 agent 对上一段是接收方，
对下一段是交接方——同一个主体的两副身份。

| 阶段 | 做什么 | 退出条件 |
|---|---|---|
| **接** | 读交接物 + spec + 代码 → 审查 → 不合格就**申诉**，与上一段循环直到合格 → 签验收 | 签了验收 |
| **做** | 只开发自己这一段，到本段能独立验证为止 | 本段验证通过 |
| **交** | 写 / 完善交接文档 → 拉起下一段（只给坐标） | 下一段已启动 |
| **守** | 留在场应答下一段的申诉，改自己那段 | **下一段签了验收** |

- 申诉与应答是「接」和「守」里**同一个循环的两端**，分属两个 agent，不是两个顺序步骤。
- 「接」未完成，上一段不得退出；「守」未完成，本段不得退出。
- **链首**没有「接」。
- **接手停滞工作时，它自带的记录一律重验，不采信。** 没有活的前任可申诉，那些记录就是唯一线索，
  而它们恰恰最容易过时或失真：说"这棵树是干净的"（其实又积了增量）、把待办先勾成已完成（先勾后审=谎报）、
  红绿计数停留在旧版本。重验成本是一次定向跑测，采信错记录的代价是整条链建在假前提上。
- **链末必须是收口段**：不开发，只做审查 + 验收档验证 + 提 PR + 处理 PR（CI 红也归它）。
  理由：链式 maker-checker 里，最后一个开发段没有后继接收方，会缺一次同行审查。
  收口段补上这一环。

「守」为什么值得付成本：申诉的应答需要**原始决策上下文**（为什么这么写、试过什么）。
换一个 agent 读代码能改，但改不出原意图。进程被回收时按磁盘交接物重建，
并在交接物里补记"上下文已重建"——责任仍归原段，只是载体换了。

## 3. 段的判据

### 下界（防碎）

一段 = **可独立验证 ∧ 可独立归责**的变更单元。

- 可独立验证：能自己从红到绿，一个验证循环不得跨段。
- 可独立归责：只覆盖一个根因或一条 spec 场景。混两个根因，申诉时判不出是谁的问题。

凑不满这个原子的候选段，并入同根因的相邻段。

### 上界（防一个人干完整片）

三条容量，任一触顶就拆：

| 容量 | 判据 | 为什么是它 |
|---|---|---|
| 审查容量 | 下一段能一次读完 diff + 相关 spec 并作出判断 | 交接是强制审查，审不动等于没审 |
| 上下文容量 | 实现者一个上下文装得下 spec + 交接物 + 被改代码 | 装不下就退化成瞎猜或反复勘察 |
| 验证容量 | 本段验证能在可接受时间内跑完 | 至少跑两遍：实现者一遍、审查者一遍 |

### 段数不是越细越好

每段冷启动要重读 spec + 交接物 + 相关代码，这个成本**随段数线性增长，质量收益不线性增长**。
段要大到能摊薄冷启动读取，小到能被一次审懂。碎段是真金白银的浪费。

### 定线方法（落地时才填数）

取项目自己声明的产物预算；没有声明，就取近期**通过审查**的样本带宽上沿。
机械段（零行为变更的移动 / 删除 / 改名）按原子性豁免数量线——拆开反而破坏可验证性——
但不得混入任何行为改动。

### 拆分顺序

先按接缝三分：**机械 / 行为 / 收尾登记**。仍超容量再按模块拆。
收尾登记（索引、清单、基线一类派生产物）永远单独成段，因为它必须最后跑且顺序固定。

### 段 = 交接单元 = 提交单元 = 评审单元

三者对齐是机制要求，不是偏好：评审证据绑定的是**一次暂存内容的摘要**，
天生就是"一次暂存一次评审"。对齐后，接收方的验收**天然就是**独立评审证据，
不需要另派评审者，也不需要主 agent 中转。不对齐就要额外造一层映射。

RED 证据放**交接物**（红测输出 + 转绿输出），不靠 commit 顺序证明。
有输出比只有顺序更强，也避免把一个验证循环切成多个提交。

## 4. 风险分档：成本按风险分配，不均摊

| 档 | 什么样的段 | 审查深度 | 验证范围 |
|---|---|---|---|
| **机械** | 零行为变更的移动 / 删除 / 改名 | 轻：一条扫描或收集命令能证明即可 | 收集 + 扫描 |
| **量具** | 测试、遥测、文档、评估代码；默认值不变的开关 | 中：看它是否真的量到了目标 | 定向 |
| **行为·核心** | 改判定、改数据、改唤醒、碰核心模块 | 全额：逐条对照 spec 与不变量 | 定向 + 相关回归 |

一视同仁是浪费：删一个已死模块和改信用结算逻辑，不该付同样的审查成本。
**质量投入应当集中在高风险档，而不是摊平。**

体量超标的处置是**要求拆分或额外审查**，不是扣分——变更体量用于风险识别，不用于评分。

## 5. 交接物（固定字段）

```
段 ID / 分支 / 工作树绝对路径 / 段起点 sha / 段末暂存摘要
本段做了什么：spec 条目 ↔ 代码位置(file:line) ↔ 测试名
验证证据：跑过的命令 + 输出摘要（含 RED → GREEN）
未完成 / 已知缺陷 / 悬置决策（各带落点）
下一段的 spec 引用与边界
历次申诉与裁决
```

交接物是**省 token 的产物**，前提是它比代码短且准：下一段本来就要知道上一段做了什么，
文档把"重新勘察代码"换成"读一份摘要"。写得比代码还长，就是失败。

## 6. 申诉协议

- 接收方发现问题，**不动上一段的代码**，写申诉。自己扛下来改，责任就糊了。
- 交接方改自己那段，回写裁决；接收方复审。
- 循环期间双方在场（见 §2「守」）。
- **轮次有上限**；超限才升级到主 agent。主 agent 只在这种异常里出现。
- **等待有超时**。任一方死亡后，协议状态在磁盘上，重开一个 agent 读状态即可续，不丢工作。

协议状态必须落磁盘，不能只活在 agent 上下文里。半成品与未裁决的申诉要能被外部看见——
这是"停在半路"能被发现的唯一途径。

### 链状态的最小形状

**过程产物一律放仓库外，不是靠 .gitignore 挡。** 链状态、交接物、申诉与裁决、验证回执、
跑测记录、证据 dump 是**同一类**：它们记录"我们怎么干的"，既不是产品也不是规格。
放进被跟踪的目录树里，一条 `git add <dir>/` 就把它们扫进提交——ignore 规则挡不住
被显式 add 的文件，也挡不住树里新开的子目录。物理上不在仓库里，才是真的进不去。

链首在**仓库外**的过程目录建 `<chain-id>/chain.json`（具体路径由项目声明，见 §10），
每段推进时更新自己那一行：

```json
{
  "schema": "dev-chain/2",
  "chain": "<切片或任务 id>",
  "branch": "<分支>",
  "segments": [
    {"id": "s1", "kind": "develop",  "owner": "<agent id>",
     "status": "working", "updated_at": "<ISO8601 Z>"},
    {"id": "s2", "kind": "develop",  "owner": null,
     "status": "pending", "updated_at": null},
    {"id": "end", "kind": "closeout", "owner": null,
     "status": "pending", "updated_at": null}
  ]
}
```

- `status` ∈ `pending` / `working` / `handed_off` / `accepted`。**它是唯一的权威状态字段**：
  收口段完成（PR 已合并，或明确放弃）就置 `accepted`，**不要只把结果写进自定义的辅助字段**——
  扫描器读 `status`，辅助字段写着"完成"而 `status` 停在 `working`，一条已合并的链会被误读成停滞，
  正好是载体要防的反面。（第一条链就这么错过一次。）
- `kind` 只有 `develop` 与 `closeout`；**最后一项必须是 `closeout`**（§2）。
- 段清单在链首一次写全（任务提前拆好），不是边做边加。
- **机械化形状（`dev-chain/2` 起）**：`kind=closeout` 的段 `status=accepted` 必须带
  `merge_sha`（PR 合并提交；读侧会核实它是 `origin/dev` 的祖先）或显式 `abandoned` 理由，
  两者皆无或二者皆有 = 非法记录。`dev-chain/1` **仅限 N0/S1/S2/S13/S17 五条历史链**
  （读侧按其时规则放行）；新记录必须 `dev-chain/2`——白名单外的链声称 v1 = 非法记录。
  界必须有形：v2 起一切机械化，不会有新的合法 v1 记录；下一条链抄上一条的 record 当模板，
  若 v1 容差无界，一次正常抄写就让 closeout 证据规则整体失效且无迹象（正是 #1079 要防的
  失败类）。
- **`owner` 与 `status` 不得互相矛盾**：`pending` 的行 `owner` 必须为 `null`
  （有 owner 却 pending = 记录落后于事实）；`working` / `handed_off` 的行必须有
  `owner` 与 `updated_at`。
- **停滞可被看见**：读侧报出「仍 `working` 但 `updated_at` 超过阈值」的行——那是停滞信号，
  正是载体存在的理由。阈值由调用方声明（`--stale-hours`，默认 12 小时）。
- **触发点（不新增常驻机制）**：主 agent 启动下一条链时读链状态、每段「接」时读链状态——
  这两处本来就在读。不做空闲轮询、不挂常驻钩子。这是它与先前被撤回的『过程门』的区别：
  那次撤回的理由是 pre-commit 在停工时根本不运行（无提交即无钩子），检查没有触发点；
  本形状只在记录**本来就被读写的时刻**校验。
- 交接物与申诉记录放同目录：`<chain-id>/<段 id>/{handoff,review,appeal-N,resolution-N}.md`。
- **不属于这一类的，照常入仓**：规格产物（proposal / design / tasks / spec）、schema 契约、
  产品测试夹具、设计裁决文档。分类判据不是文件名，是**它描述产品应该是什么样，
  还是描述我们干过什么**。`validation.md` 这种名字既可能是规格也可能是回执，看内容。
- **量具与 spike 要分开**：可复用的量具（反复用来复现某个数字的工具）是开发脚手架，
  放项目声明的开发工具目录，入仓；**一次性 spike 脚本连同它的跑测记录**是过程产物，出仓。
  判据是"下次还会用它吗"，不是"它是不是实验"。把量具一起赶出去，等于每次重造尺子。
- 例外：路径被工具写死的门证据（如评审回执、mint 令牌）留在工具要求的位置，
  但必须整目录忽略、永不入仓。

先用普通 JSON 读写，不预先建校验器：形状被第一条链真实用过之后，再决定要不要机械化。
**2026-11-25 条件已满足**：形状已被五条链（N0/S1/S2/S13/S17）真实使用，出现两次失真
（#1079：S2 两段 accepted 而 PR #1076 未合并——记录超前于事实；S13 收口段已工作约两小时
而自己那行仍 pending——记录落后于事实）。现在机械化：读侧校验器 `devkit/chain_acceptance.py`
（跨平台 Python；`dev-chain/2` 起生效，`dev-chain/1` 仅限 N0/S1/S2/S13/S17 五条历史链）。
它的运行时刻就是上面的触发点两处——不做空闲轮询、不挂常驻钩子；过程记录仍在仓库外，本片改的是形状与读侧，不是位置。

## 7. 质量底线：四条，一条都不能省

1. **行为改动必须被另一双眼睛看过。** 这是被反复证明能抓到真实缺陷的机制。
2. **改动必须走生产路径被验证。** 绕过生产调用点的测试，会让死线藏很久；
   一条走生产路径的测试，胜过大量绕过它的单测。
3. **段必须小到能被审懂。** 一次送审的体量超过审查容量，审查就退化成盖章。
4. **半成品必须会被发现。** 所有检查都只看产物当下是否自洽时，停在半路的工作是绿的。

## 8. 成本纪律

- 主 agent 不读代码、不中转。这是最大的一笔节约。
- **全量验证在链末一次**，段内只跑定向验证。全量跑很多遍换不来质量——
  逃逸的缺陷通常是接线与路径类的，单元测试结构上抓不到。
- 段数取最优，不取最细（§3）。
- 质量投入优先**路径覆盖**，而不是测试数量。测试数量增长但交付质量不动时，停止扩张。

## 9. 度量：先两个数

从同一份交接记录里数出来，几十行的事：

| 数 | 定义 | 看什么 |
|---|---|---|
| **首次验收通过率** | 接收方第一次审查即 PASS 的段 / 总段数 | 上游交付质量；可按段类型定位薄弱处 |
| **申诉轮次** | 每段申诉次数 | 返工量；也是缺陷被段边界捕获的记录 |

有了这两个数，才谈得上"缺陷逃逸"的正确分母：**段边界捕获 / (段边界 + 链末 + CI + 发布后)**。
用 issue 创建时间当分子分母是失真的——开发期缺陷通常不开 issue，直接改掉了。

不要一上来就接一整套 KPI。先两个数，够用很久。

## 10. 落地接口

落到具体项目时只需要填三个数和一个路径：**产物预算、审查带宽、验证时长上限**，
以及**仓库外的过程目录根**（§6；必须在仓库树之外，不是仓库内一个被忽略的子目录）。

与 devkit 的接口：

- **两档已经存在，只需要命名，不需要改机制**：提交时跑的是"除全量回归外的全部"
  （pre-commit 模板的集合，由 `tests/test_doc_sync.py` 从 GATES 注册表推导钉住）；
  链末跑默认全集（含全量回归）。前者叫**不变量档**，后者叫**验收档**。
  CI 的 `--quick` 是第三个概念——冒烟子集，与前两者无关，不要混称。
- **过程检查**（唯一需要新增的机制，2026-11-25 落地）：`devkit/chain_acceptance.py` ——
  读磁盘上的链状态，校验 §6 机械化形状（closeout 收口证据 = `merge_sha` 是 `origin/dev`
  祖先或显式 `abandoned`、`owner`↔`status` 一致、`working` 行 `updated_at` 停滞信号、
  链末必须收口段）。它是**唯一在没有暂存改动时也必须运行**的检查：现有检查要么由暂存内容
  触发（无改动即 N/A 通过），要么只看产物当下是否自洽，半成品只要自洽就是绿的。
  但它不是 pre-commit 门——触发点只有两处：主 agent 启动下一条链、每段「接」（§6）。
  调用：`python devkit/chain_acceptance.py check <record>`；
  退出码 0 = 干净 / 1 = REFUSE（记录非法）/ 2 = 不可验证（检查没跑成，不作数）/
  3 = STAGNANT（有 working 行越过停滞阈值）。
- **身份判定**：现行是名字子串黑名单。链跑起来、交接物带上作者字段之后，
  再改成"验收人 ≠ 本段作者"的精确比对；在此之前不动——没有误伤记录就没有改动理由。
