## Decisions

Use one per-workspace OS file lock across each posterior writer's read-modify-save interval. Acquire it before reading pair outcomes in the amendment path. Advisory locking shares the platform matrix's Windows and POSIX primitives; require a real lock. Incomplete or unreadable snapshots refuse every update before appending or revoking. Knowledge appends and revocations share a strict platform lock, with a distinct lock per workspace file. Discovery distinguishes missing paths from failed reads so a later reconciliation can retry. Readers can consume the existing atomically replaced snapshot without acquiring the lock. Acquisition order is posterior, experience/knowledge. No shared global lock or new journal.

The lock covers the four production posterior writers: the pair correction, both case-observation legs, the oracle verdict recorder and the question seeder. `scripts/replay_ruler.py` is the one writer outside it: it copies a posterior file into its replay sandbox with a plain file copy, and that sandbox is private to one replay process. A writer that dies releases the lock with its process. On Windows the lock primitive retries once a second for ten attempts and then raises, so a contended wait ends as a refusal after about ten seconds; this was not run on Windows.

The identity for claim-scoped derived rows is (workspace_id, claim). Match only supported negative and broadcast records, never the credit series. New attributed negatives carry the existing resolved workspace identity. A match without the historical workspace binding is unavailable. Discovery and deletion use the same classification. A failed append cannot authorize deletion. Pre-move files remain discoverable through the existing registry.

Unavailable attribution is reported where it is read. The production Stop lists the claims under `case_revocations_unavailable` in the terminal record, emits one `case_revocation_unavailable` event per claim however many Stops see the condition, and warns once per Stop. The settle CLI prints the list with its other fields.

No writer repairs a refused file: the settlement pass offers the update again on every pass and refuses again while the cause remains; an oracle verdict is not offered again. Under an armed learning seal, a ledger sealed by another build is refused by all four writers, and so is any ledger with an entry that cannot be read. The error names both builds or the unreadable entry, and the file's bytes stay as they were. The writers used to continue with the empty ledger they could read and overwrite the file. In production the terminal settlement stays in retry: it raises on the refusal of an unreadable entry, and after a build change its learning-seal check on the sealed reward rows returns retry first. An oracle verdict whose update is refused is dropped: the capture path (`scripts/outcome_capture.py`) reports it with one `oracle_cadence_warn` event. No repair path is built here; a re-seal belongs with #1055.

## Verification

Interleave real reconciliation with each of the other writers (a question seed, a second correction, an oracle verdict, a case observation) and verify the persisted effects. Exercise each kind of missing ownership (absent, legacy basename, malformed, non-string) alongside a known attributed record and an unrelated claim's record. Reconcile twice, including after reopening the workspace. Keep refusal, revocation retry and sealed snapshot coverage: a ledger sealed by another build is refused by all four writers and left untouched. The committed-append/failed-save repair is explicitly separate.
