# Design

Self-reviewed against #754's durable-registration contract (archive/issue-754-heartbeat-autonomy) and #482's fail-open ratchet style — both read.

1. **Container-key selection** — one constant, `ENTRY_KEYS = ("jobs", "tasks")`, preferred order jobs-first. Read and write SHARE the list-valued predicate — first key whose value is a list (jobs first) — so both sides always target the same container. Beyond that shared half the paths differ deliberately: a read that finds no list-valued key quarantines (r3-M1), while a write with no known container adds `jobs` and keeps every other key (first-present fallback, else default `"jobs"`). Jobs-first means a document carrying both keys keeps kunglao's entries in `jobs` and the harness's `tasks` array as foreign data the write path never touches. The shared list-valued predicate matters: read-from-`tasks` but write-to-`jobs` on a malformed `{"tasks": [...], "jobs": null}` doc would split kunglao's own entries across keys on the next run.

2. **Write is a preserve-in-place rebuild** — `_write_file` re-parses the current bytes (utf-8-sig) and rebuilds the dict: container key's value := our entries, every other key carried over verbatim, original key ORDER kept. Unknown sibling keys survive in the MAIN file (previously they only survived because the whole file was sidecar'd first, then dropped from the rewrite). Bare arrays stay bare arrays. Corrupt/unparseable bytes fall back to the old head-`{` wrapper detection so a corrupt file still rebuilds as `{"jobs": [...]}` exactly as before.

3. **Sidecar backup retained, not weakened** — the sibling-key case (`len(data) > 1`) still writes the `*.unrecognized-*` sidecar even though the rewrite now preserves siblings. Rationale: r3-M1's contract is "never a silent clobber" — the sidecar is the receipt, the in-place preservation is the fix. Removing it would break `test_unrecognized_but_valid_shape_backed_up` (#754) for zero user benefit. Fail-open: anything we still don't understand backs up before rebuild.

4. **The `tasks` shape is RECOGNIZED, not special-cased** — no quarantine sidecar for a pure `{"tasks": [...]}` file (that quarantine WAS the bug: kunglao's entries exiled, harness's key destroyed). The recognition boundary stays explicit: only `jobs`/`tasks`/bare-array are ours to rewrite; everything else keeps the old READ semantics (quarantine + treat as empty) while the WRITE path now retains unknown data in the main file instead of dropping it (spec R3 scenario 2) — old behavior, strictly better.

5. **Byte-identity negative control** — harness records pass through a full upsert round-trip byte-for-byte (indentation included): `_write_file` never touches non-container values and never reorders their dict keys (Python dicts preserve insertion order through json round-trips). Test 4 asserts the exact serialized blob survives.

6. **Blast radius** (GitNexus `impact --direction upstream --depth 1`): `_read_entries` — 3 direct callers, `_write_file` — 2; ALL in-module (`loop_entry_exists`, `upsert_durable_loop`, `remove_durable_loop`). Risk LOW at d=1; the depth-3 CRITICAL rating is graph-transitive noise through unrelated processes. No signature changes → no caller updates. The other `scheduled_tasks` mentions (`kunglao-init.py`, `kunglao.py`, `heartbeat_loop_prompt.py`, `worker_budget_sinks.py`) are message strings / upsert call sites, not JSON parsers.
