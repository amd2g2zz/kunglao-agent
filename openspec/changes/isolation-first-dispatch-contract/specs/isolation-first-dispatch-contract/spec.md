## ADDED Requirements

### Requirement: Agent SHALL be the only dispatch tool; the repo SHALL contain no stale Task-tool references

The kunglao-agent dispatch contract SHALL use the `Agent` tool as the only dispatch tool. No tracked file (`SKILL.md`, `references/*`, `hooks/*`, `scripts/*`, `agents/*`, `.claude/*`) SHALL contain a reference to the nonexistent `Task` tool — precisely: the phrase `Task tool`, a backtick-quoted `` `Task` `` naming the tool, or a `Task` entry in an agent definition's `disallowedTools` list. Legitimate tokens (`TaskStop`, `TaskList`, `task_spec`, `task-oracle`, the English word "task") SHALL remain untouched. `hooks/dispatch_gate.py` SHALL retain its payload-shape robustness (the `prompt`/`description`/`task`/`input` field fallbacks, still valid for Agent tool inputs) while its docstrings and comments name the `Agent` tool.

#### Scenario: repo-wide grep finds no stale Task-tool references

- **WHEN** a repo-wide grep runs over `SKILL.md`, `references/`, `hooks/`, `scripts/`, `agents/`, `.claude/` for the stale patterns (`Task tool`, backtick-quoted `` `Task` ``, tool-entry `- Task`)
- **THEN** the grep returns zero matches, and the matches for `TaskStop` / `TaskList` / `task_spec` / `task-oracle` remain untouched

#### Scenario: agent definitions no longer disallow a nonexistent tool

- **WHEN** any `agents/*.md` definition is inspected
- **THEN** its `disallowedTools` list contains no `Task` entry, and its dispatch surface names the `Agent` tool

### Requirement: The isolation-first hard rule SHALL be written into the dispatch contract — no agent teams; SendMessage orchestrator↔worker pings remain the sanctioned heartbeat channel

`SKILL.md` §1 (Tool-use boundary) and §"The dispatch contract" SHALL state, as a hard rule: kunglao tasks never use agent teams — `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` SHALL NOT be enabled, no teammates are spawned, no team setup is performed (teammates are separate Claude instances with a shared task list and mailbox, which breaks subagent isolation); workers are always isolated subagents that report only to the orchestrator, and workers never communicate with each other. The same sections SHALL state that SendMessage between the orchestrator and its workers is NOT a team feature and remains allowed: the heartbeat active-ping (orchestrator → worker) and worker replies are the sanctioned channel. `references/cold-start-contract.md` Phase 0 SHALL carry the same rule plus the cautionary note that the machine-level env flag was the 2026-08-12 root cause of the misdiagnosed dispatch regression, that it has been removed, and that a session showing team directories or teammates means the contract is violated.

#### Scenario: SKILL.md carries the isolation-first rule in §1 and the dispatch contract

- **WHEN** `SKILL.md` §1 and the "The dispatch contract" section are read
- **THEN** both sections contain (a) the no-agent-team statement (no `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`, no teammates, no team setup), (b) the statement that workers are isolated subagents that never message each other, (c) the statement that orchestrator↔worker SendMessage pings are allowed, (d) the TaskStop-on-delivery statement

#### Scenario: cold-start contract documents the flag root cause

- **WHEN** `references/cold-start-contract.md` Phase 0 is read
- **THEN** it states the isolation-first rule and records that `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` was the removed machine-level root cause and SHALL NOT be re-enabled

### Requirement: The heartbeat active-ping SHALL use SendMessage (orchestrator→worker); worker status files SHALL remain the accounting source of truth

The heartbeat ping procedure SHALL keep the v1.9.20 SendMessage active-ping (orchestrator → worker, smart-ping protocol: `[ping HH:MM] step? stuck? eta?`), and worker replies via SendMessage SHALL count as liveness signals. File state SHALL remain the accounting source of truth: worker liveness and delivery SHALL be confirmed against `worker-status-<id>.md` freshness + last status line, read-only `TaskOutput(task_id, block=false)` cross-checks, and `[active_workers]` slot accounting rebuilt by `scripts/reconcile_workers.py`. The 3-strike protocol SHALL stand: strikes accumulate on a pinged worker with no status-file append / artifact touch / SendMessage reply within threshold; three strikes → TaskStop + redispatch. This procedure SHALL be reflected in `references/operational-mechanics.md`, `references/guardrails.md` (§6.1a / §6f.1), the prompt generated by `scripts/heartbeat_loop_prompt.py`, the option (a) text of `scripts/active_intervention.py`, and `scripts/kunglao-monitor.py`. None of these SHALL instruct agent-team setup or worker↔worker messaging. `scripts/kunglao-monitor.py` SHALL be documented as a background process: it never blocks the loop's scheduled tick actions (re-dispatch / verify) — the loop tick SHALL NOT wait on monitor output before proceeding. `agents/kunglao-redteam.md` SHALL deliver its verdict via its report file under `runs/` and its dispatch return (final report), the reliable channels for isolated subagents.

#### Scenario: heartbeat mechanics keep SendMessage ping with file-state accounting

- **WHEN** `references/operational-mechanics.md` heartbeat tick loop and `references/guardrails.md` §6.1a/§6f.1 are read, and `scripts/heartbeat_loop_prompt.py` output is generated
- **THEN** the ping step uses SendMessage (orchestrator→worker), worker SendMessage replies reset strikes, status-file freshness + read-only `TaskOutput` remain the accounting cross-checks, and none of them instruct agent-team setup or worker↔worker messaging

#### Scenario: worker help-request responses use the established file channel

- **WHEN** `scripts/active_intervention.py` and `scripts/kunglao-monitor.py` are read
- **THEN** the workaround response option is "append `## orchestrator_response` to `heartbeat_actions.md`" (the existing response channel), with no agent-team alternative

#### Scenario: the monitor runs in the background, never blocking the loop

- **WHEN** `references/operational-mechanics.md` heartbeat tick loop and `scripts/kunglao-monitor.py` are read
- **THEN** kunglao-monitor.py is documented as a background process whose output the tick does not wait on — the loop's scheduled actions (re-dispatch, verify) proceed without monitor results

#### Scenario: the red-team agent delivers by file and dispatch return

- **WHEN** `agents/kunglao-redteam.md` is read
- **THEN** it names its `runs/` report file as the verdict deliverable received through the dispatch return, and contains no `- Task` disallowedTools entry

### Requirement: A delivered worker SHALL be TaskStop'd on delivery confirmation

The dispatch contract SHALL require the orchestrator to TaskStop a background worker immediately after delivery confirmation — the worker's status file shows a final state (`done` / `blocked`) AND its artifacts are verified — before any further dispatch/verify action. The rule SHALL be stated in `SKILL.md` §"The dispatch contract" with a delivery checklist in `references/operational-mechanics.md`. Mechanically, `hooks/worker_pulse.py` SHALL, on a dispatch-completion PostToolUse whose worker status file shows a final state, inject a `TASKSTOP: W-<n> delivered — TaskStop now` reminder into the pulse output. `scripts/reconcile_workers.py` SHALL continue to exclude `done` workers from `[active_workers]` (slot accounting self-heals).

#### Scenario: SKILL.md states TaskStop-on-delivery

- **WHEN** `SKILL.md` §"The dispatch contract" and `references/operational-mechanics.md` delivery checklist are read
- **THEN** both require the orchestrator to TaskStop a worker whose delivery is confirmed (final status + verified artifacts), and `operational-mechanics.md` orders it before dispatch-verifier/registry actions

#### Scenario: worker_pulse reminds TaskStop at the delivery moment

- **WHEN** `hooks/worker_pulse.py` runs on a dispatch-completion payload whose worker status file shows `status: done`
- **THEN** its output contains a `TASKSTOP:` reminder naming the delivered worker, and a worker whose status file shows `in-progress` produces no such reminder

#### Scenario: delivered workers do not hold slots

- **WHEN** `scripts/reconcile_workers.py` runs against a worker whose last status line is `done`
- **THEN** the worker is not counted in the rebuilt `[active_workers]` segment
